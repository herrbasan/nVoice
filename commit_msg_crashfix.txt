fix crash on realtime session close; make silent crashes diagnosable

Root cause of the chat-app "works once, then crashes": the retirement commit
removed the ?assistant=1 state (pauseTimer/paragraphTimer) but the
browserWs.on('close') handler kept referencing it — one of the batched edits
had failed silently and the close path was never re-checked. EVERY realtime
session close threw ReferenceError → uncaught → process exit 1. Reached the
chat app as: first dictation session works, socket closes, server dies.

- server/api/realtime.js: close handler reduced to turnMachine.close() +
  workerWs.close(); swept for every other orphaned reference from that batch
  (none left).

- Crash reporter fixed twice over, both bugs found by reproducing the real
  crash with tests/test_concurrent_repro.mjs:
  1. called a non-existent logger.fatal() — threw inside its own catch and
     exited silently;
  2. used process.cwd() (server/) and __dirname (undefined in ESM) for the
     log path — crashed at LOAD time before the handlers registered.
  Now: synchronous stderr write + appendFileSync to logs/main-0.log and
  logs/crash.log (relative to the module, not cwd), plus a process 'exit'
  hook so an explicit exit is recorded too.

- tests/test_concurrent_repro.mjs: three concurrent realtime sessions
  streaming, concurrent cleanup POSTs, abrupt terminate — the recipe that
  reproduced the crash deterministically. Keep it as the regression test.

Lesson recorded: a failed multi-edit is silent — the batch reports which ops
failed, and the unapplied ones must be re-verified, not assumed. This one cost
a day of blind guessing.
