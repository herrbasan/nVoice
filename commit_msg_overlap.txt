fix TtsPlayer overlapping playback: reserve the slot before the decode

Issue #3. _schedule() guarded on `_source` alone, but _startSource assigns
`_source` only AFTER its awaited decode — so the guard was open for the whole
decode and a second sentence could start alongside the first. Audible as
amplitude stacking ("progressively louder") that never recovered, because each
stale src.onended bailed out early and left _runActive set. iOS-only in
practice: a slow decodeAudioData widens the window, and streaming tokens into
push() drives _schedule() on every token.

- _play() reserves the slot (_starting = true) BEFORE any await; _schedule()
  guards on "starting OR playing", so the window is closed at the source.
- _startSource() clears the reservation on every exit path (early return,
  throw, and once _source takes over); stop() releases it too, so a cancelled
  start cannot wedge the player.
- _startSource() refuses outright if a source is live — checked BEFORE the
  decode, so a refused sentence is neither decoded nor stacked; it is kept at
  the front of the queue for the current source's 'onended'. Reported via a new
  'overlap-prevented' event and stats.overlapPrevented.
- state now exposes `starting`.

tests/test_tts_overlap.mjs — 20 checks driving the real scheduler with a
controllable decode: concurrent _schedule during a pending decode starts
exactly one source; normal onended progression still works; stop() mid-decode
releases the slot and does not wedge; a direct second start is refused and
reported. test_tts_ios.mjs still 13/13.
